# FirstField: a second genuine random key and saved world

On 2026-11-02 the original Cobi game awarded a **different Magic Key** from the previously played QuietSea key. This was observed under Wine using the archived full-ROM diagnostic from game source `1351bcd058e491455a477045a2ff86bbc3bd7b1c`, EXE SHA-256 `61a0e6d3ff84b5322b101247fc93ff6889f123a1bcd94df663135757fb3b9855`. The player used original controller input; no game memory, RNG or Journal bytes were injected or edited.

The input was the independently verified original Octokid-training Journal, SHA-256 `1e1f07c5042f69743a9ecfc3974aabfcc39a88b5863e755bd2897bc72fe9edee`. The retained original C-class route was replayed with 32 extra no-button frames at frame 34957, **after** the original champion announcement. Observational assertions after the changed timing were omitted for the exploratory run; original game actions continued, its original Journal was written, and a fresh Continue passed. The resulting C-class Journal SHA-256 was `a6d6dacf08d0ac86838a26bb797076916938b693f4ff2d92090317ccd70576cd`.

Compared byte-for-byte with the earlier original C-class Journal, only seven bytes differed: offsets `3c17`, `3c18`, `3c90`, `3c91`, `3d30`, `3d31` and `3f98`. The new unappraised key record was `fe 04 14 08`, with little-endian seed `27 19` (0x1927); the earlier QuietSea key used `fe 07 13 08` and seed 0x16C0.

In the original Key Shop the player chose the unknown key and paid the actual 90G fee (160G to 70G). The original dialogue identified it as **FirstField**. A second original Journal and fresh Continue passed; its SHA-256 was `67f0ccce0a65951e8dbab96d24e9f753a5c9cf916ca89340afec84da7fe4c7cf`.

The player entered the original key room and used FirstField. The game generated a second random world and entered its castle; the random context was `00 00 87 00`. The existing diagnostic `journal` convenience command rejects the original random-world field submode `1:5` before sending input, so the session was replayed and the player selected the original **PLAN > Journal** menu manually. The game displayed “Your progress has been recorded.” The unchanged 32 KiB cartridge SRAM after that original confirmation was copied as a Journal (SHA-256 `55b117bab52296d990e904f3736474c7a7ccdf81e2ecfc10d31805c72ed59609`) and loaded in a new diagnostic process using original Continue input.

Fresh Continue restored the FirstField castle, the same random context, all 128 key-record bytes, 64 seed bytes, 107 quest bytes and the complete 404-byte world descriptor. The descriptor matched the original Journal's working and backup caches. The entire fresh SRAM was byte-for-byte identical to that Journal. No saves or executables are included in this evidence directory.

The exact verified production EXE (`63bf283dfeb7543c82d2787221788ab71e8651130b0a829b8987b368864a6f95`) was separately launched under Wine with an independent copy of that real Journal. Original Continue input reached the same FirstField castle, and the process exited normally. Its complete saved SRAM, key records, seeds, 107 quest bytes and both cache regions remained byte-identical. See the [production save card](production-save-card.bmp), [production fresh Continue](production-fresh-continue.bmp), [exact observation](production-continue-observation.json) and [probe](production-continue-probe.py). The probe imports the earlier local VS helper and uses scratch paths; the archived script alone is not a self-contained reproduction. This is not a native Windows execution claim.

The same production EXE was then launched from the independently copied **appraised, not-yet-generated** FirstField Journal. Original keyboard input reached the key door, used FirstField, [generated its castle](production-generated-castle.bmp) and produced the [original Journal confirmation](production-journal-confirmed.bmp). The exact produced key records, seeds, 107 quest bytes and complete 405-byte working and backup caches matched the diagnostic observation; the process shut down normally. A second production process loaded that exact resulting Journal (SHA-256 `11de7ea4ebcda84ff66dd1035df7754f92dd899ba19d286a57d2c2e6ca5a0335`) via original Continue, [reached the castle](production-generated-fresh-continue.bmp) and shut down normally with the entire Journal unchanged. See the [generation report](production-generation-observation.json), [fresh Continue report](production-generated-fresh-observation.json), and [input helper](production-generation-probe.py). An initial attempt reached the original save prompt but timed out because its helper expected the confirmation too early; that automation failure remains in scratch.

The observed descriptor identifies FirstField as terrain class 3, recipe 9, size 4×4; the previously observed QuietSea descriptor identifies terrain class 8, recipe 13, size 4×4. Their complete descriptor SHA-256 values differ. These indices are read-only observations of the game's original generated state, not supplied inputs. The [read-only original-ROM map analysis](world-readonly-source-observation.json) also matches the currently observed 360 tile bytes and identifies a four-floor type-4 structure and a three-floor type-5 structure; it does not demonstrate that either was navigated.

An earlier attempt adding eight idle frames at the title instead diverged and failed to produce a valid Journal. It was preserved in scratch and is **not** evidence of a game/runtime defect. The current evidence establishes one additional genuine key/world and its persistence, not all seeds, terrain classes, generated rewards or native-Windows acceptance.
